SDLC Harness — New Team Member Onboarding Runbook

Time to complete: 20–30 minutes on a machine that already has Docker and Node.js.

Prerequisite checklist, confirm before you start:

Step 1 — Create your local credentials file

The .env files are gitignored and must be created locally. Copy the examples:

install -m 600 gitlab-local/.env.example gitlab-local/.env

Open gitlab-local/.env and replace both GITLAB_ROOT_PASSWORD and GITLAB_DEMO_PASSWORD with strong, distinct values. The latter is the login password for the non-admin demo user.

⚠️ Do not commit .env files. The .gitignore already covers them; this is a double-check.

Step 2 — Start the Docker stack

From the gitlab-local/ directory:

cd gitlab-local
./manage.sh start

GitLab CE takes 3–5 minutes to initialise on first boot. ./manage.sh start blocks until the host-facing GitLab sign-in page, GitLab's internal readiness check, and the demo site all pass (300s timeout). It then runs the complete idempotent seed. ./manage.sh restart performs the same readiness checks and seed reconciliation. Expected health output includes:

✓ GitLab sign-in returned HTTP 200
✓ GitLab internal readiness returned HTTP 200
✓ Demo site (weather app) returned HTTP 200
All checks passed — GitLab and the demo site are healthy.

If it times out instead, check ./manage.sh logs for errors before continuing. You can re-run the health check without restarting, or explicitly reconcile the complete seed, at any time:

./smoke.sh
./manage.sh seed

The automatic seed creates or reconciles:

  • A SDLC Harness GitLab group at /sdlc-harness
  • A demo user (Developer role)
  • The weather-dashboard project with source files pushed

It also populates the weather-dashboard project with 12 issues that have missing acceptance criteria, vague descriptions, broken dependency links, and missing test coverage, exactly the signal each P0 agent needs to act on in the demo.

At the end you will see the project URL and deterministic agent-fixture summary. Passwords are deliberately never printed.

Step 3 — Install and build the MCP server

Return to the project root (sdlc-harness/):

cd ..
bash bob-kit/mcp-server/install.sh

This:

  1. Checks Node.js ≥ 18.18
  2. Installs, tests, and builds both the skill runtime and MCP server
  3. Merges the sdlc-harness MCP server entry into ~/.bob/settings/mcp.json without overwriting any other servers you have configured
  4. Merges the 🔧 SDLC Harness mode into ~/.bob/settings/custom_modes.yaml
  5. Runs the mock smoke test to confirm the build is healthy

Expected output ends with:

✓ Smoke test passed
==============================
Installation complete.

Step 4 — Configure MCP server credentials

The MCP server is a stdio server that Bob spawns itself — there's no separate process to start — but it reads its config from the project root .env (via SDLC_ENV_FILE, set automatically when Step 3 merged Bob's config), not from anything inside bob-kit/mcp-server/. Getting this file wrong is the most common cause of the MCP server showing Disconnected in Bob with no further explanation: it exits immediately at startup if any of these are missing, silently unless SDLC_DEBUG=true.

From the project root (sdlc-harness/), create the file with owner-only permissions if it does not exist:

install -m 600 bob-kit/mcp-server/.env.example .env

If .env already exists, merge the variables below instead of overwriting it and run chmod 600 .env.

Open the project-root .env and set:

VariableValue
GITLAB_HOSThttp://localhost:8080
GITLAB_PROJECTsdlc-harness/weather-dashboard
GITLAB_TOKENA Personal Access Token (see below)

Creating a Personal Access Token:

  1. Log into GitLab at http://localhost:8080 as demo (password from Step 1).
  2. Go to User → Edit profile → Access Tokens.
  3. Create a token named sdlc-harness-mcp with api scope and any expiry you like.
  4. Copy the token value into GITLAB_TOKEN in the project-root .env.

Alternatively, ./gitlab-local/manage.sh refresh-token mints, writes, and verifies a scoped token in the project-root .env without displaying it.

Step 5 — Run the live smoke test

Confirm the MCP server can reach GitLab, reading the same project-root .env Bob's spawned server will use (this command's default working directory would otherwise resolve a different, local .env inside bob-kit/mcp-server/):

cd bob-kit/mcp-server
SDLC_SMOKE_LIVE=true SDLC_ENV_FILE="$(cd ../.. && pwd)/.env" npm run smoke

Expected output: all checks pass and your GitLab username is printed.

If this step fails, check GITLAB_TOKEN, GITLAB_HOST, and GITLAB_PROJECT in the project-root .env (Step 4).

Step 6 — Open Bob and activate the sdlc-harness skill

Bob supplies the built-in model; no provider or model configuration is required. The skill controls when generation is invoked, not which model runs it. It uses generation for acceptance-criteria and ambiguity prose, while dependency, transition, and coverage detection are deterministic.

  1. Restart Bob so it picks up the newly merged config (close and reopen, or use the reload command if your IDE supports it).
  2. In the Bob mode selector (bottom-left of the chat pane), choose 🔧 SDLC Harness.
  3. Type the following to activate the skill and start onboarding: 
    govern my backlog
    Bob will detect that the project has not been onboarded yet and start the guided onboarding conversation (Task 18 / Phase 1 of the skill).

Step 7 — Complete the onboarding conversation

Bob will ask four questions. Use the values below for the demo project:

QuestionAnswer
Which GitLab project should be governed?http://localhost:8080/sdlc-harness/weather-dashboard
What work item types does the team use?Story, Bug, Task
What are the workflow states?Open, In Progress, In Review, Done
What are the transition rules?Open→In Progress; In Progress→In Review; In Review→Done

Bob will save this configuration to .sdlc-harness.json in the repo root and confirm it is ready to monitor.

Step 8 — Verify the audit and review loop

After onboarding, Bob should print a confirmation summary and offer the governance action menu:

✅ Onboarding complete. Governing: sdlc-harness/weather-dashboard

What would you like to do?
  • Audit all open issues
  • Review and apply a finding
  • Show the telemetry summary

Type audit to confirm the agents can reach the seeded issues and produce findings. Audit is read-only. Bob presents each finding with apply/edit/skip/reject choices; only apply and edit write through the guarded review runtime, while reject records the decision and skip is not logged.

Maintenance and cleanup

Run these commands from the repository root:

GoalCommand
Rotate and verify the demo-user API token./gitlab-local/manage.sh refresh-token
Restart, wait for readiness, and reconcile the complete seed./gitlab-local/manage.sh restart
Wipe GitLab data and reseed a clean demo./gitlab-local/manage.sh reset
Remove only Bob-side assets and build outputbash bob-kit/mcp-server/uninstall.sh
Return the full demo to a freshly cloned state./gitlab-local/manage.sh uninstall

The full uninstall is destructive: it removes Docker volumes, local .env files, onboarding state, telemetry, build artifacts, and the sdlc-harness Bob registrations. It prompts before proceeding.
