Agents and Tools

What is inside the sdlc-harness skill: five agents that inspect work items, and five MCP tools they use to reach GitLab. This page is the reference for both the documentation set and the presentation.

The rule that shapes everything

The agents detect. They never write. An agent inspects one issue, decides whether something is wrong, and returns a finding. It has no path to GitLab of its own. Every change reaches an issue through the review interface, and only after a person approves it.

This is enforced in code, not by convention. Each agent is a pure function: it takes an issue, returns a finding or null, and performs no network calls. The write path lives in review.ts, and applyFinding() throws if it is handed a finding whose text has not been drafted yet. Placeholder text cannot reach a real issue.

The second rule matters as much: where the issue does not say something, the agent asks rather than invents. Every finding carries an unknowns list, which is the set of gaps the issue does not fill. Those become direct questions to the author. A confident, plausible, made up value is worse than no value at all, because it looks finished.

The five agents

Acceptance criteria (AC)

Finds issues with no acceptance criteria and drafts them in Given-When-Then form, grounded in the issue's own title and description.

Detection is deterministic. An issue is treated as already having criteria if the description contains an Acceptance Criteria heading, ## AC, ## Criteria, or a structured Given / When / Then block where each clause opens its own line. Three keywords inside a sentence of ordinary prose does not count, which is why a line like "Given the deadline is tight, when we ship this, then keep scope small" is correctly ignored.

The agent fetches the format from the work-item-format tool rather than holding a second copy of the standard, so a Bug gets Bug structure and a User Story gets story structure.

Ambiguity (AM)

Finds wording that cannot be tested against, and proposes a rewrite that keeps the author's meaning.

It flags five categories: placeholders (TBD, TODO, FIXME, XXX), non specific pronouns ("the thing", "something", "somehow"), vague subjects ("fix it", "it doesn't work"), non testable claims ("does not work"), and vague quantities ("various", "several things"). The finding names the exact phrases, so the rewrite replaces those spans and leaves the rest of the description alone.

To avoid false positives, a description of at least 80 characters carrying two or more specificity signals (file paths, inline code, URLs, API or endpoint or class references) is left alone even if one loose word appears.

Dependency (DEP)

Finds issues that describe the same work and proposes a link between them.

Overlap is measured with Jaccard similarity over keyword tokens, with stop words removed. Pairs scoring below 0.12 are ignored; above 0.25 the confidence is raised. The agent proposes blocks when one issue contains dependency language, and relates-to when it does not. It never produces self links or duplicate pairs.

These links are written for real. createIssueLink() in gitlab-client.ts calls GitLab's issue links API, so an approved dependency finding creates an actual relationship in the project.

State transition (ST)

Finds issues whose state is stale compared to merge request activity.

A merged merge request against an open issue proposes In Review. An open merge request proposes In Progress. With no linked merge request there is no signal and no finding.

The agent only proposes transitions that the team's own rules allow. Valid states and transitions come from .sdlc-harness.json, written once during onboarding, and reachability is checked across those rules before anything is suggested. GitLab issues only have opened and closed, so workflow states are carried as scoped labels.

Test coverage (COV)

Cross references issues against test files and flags work items with no test reference. It looks for #12, closes #12, fixes #12 and similar patterns.

This one is off by default and has to be enabled in the project config. It is a P1 stretch item, held back deliberately until the four P0 agents were proven.

The five MCP tools

ToolWhat it does
gitlab-issue-readerReads issues, labels and comments for the configured project. Every agent starts here.
gitlab-issue-writerCreates and updates issues, with duplicate detection on title. Only the review interface calls it.
gitlab-mr-reader-writerReads and manages merge requests: list, get, create, update, merge (accept-mr), close, and comment. This is what gives the state transition agent its activity signal, and what a direct request like "open a merge request for issue #7" or "merge MR !12" uses — see the Prompt Suite for the full catalog.
work-item-formatThe canonical format standard: title conventions, description structure and Given-When-Then criteria per work item type. Single source of truth, so the agents do not each invent their own.
sdlc-review-decisionApplies or rejects a suggestion and records telemetry in one atomic step, so a decision cannot be written without being logged.

Scope

The skill acts only on the project established during onboarding. It never reads or writes issues, merge requests or labels in any other group or project on the same GitLab instance, including while scanning for dependency overlap. To govern a different project, onboarding is re run. Scope is never inferred or widened on its own.

Telemetry and the acceptance rate

Every decision appends one line to an append only JSONL log: which agent, which issue, which action, and the outcome. Outcomes are accepted, edited, rejected and failed.

failed exists for a specific reason. If a write does not reach GitLab, the decision is recorded as failed and excluded from both sides of the acceptance rate fraction. Without it, the rate would count writes that never happened, and the number the demo cites would mean nothing.

That number is the point of the whole system. It is not "here is a feature", it is "here is evidence the team is accepting most of what it sees". A rate that climbs means the agents are learning the team's conventions. A rate that stalls means they are adding noise.
