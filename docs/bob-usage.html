How Bob Was Used to Build This

This describes how the team used the IBM Bob IDE during development of sdlc-harness. It's distinct from how the shipped product uses Bob at runtime, which is covered in Problem Statement & Solution and bob-kit/skills/sdlc-harness/SKILL.md. Every session referenced here has a corresponding screenshot in bob-sessions/, captured as the build progressed rather than reconstructed afterward.

Planning and problem framing

The to-do list this project was built against wasn't written by hand and then handed to Bob to execute; Bob wrote the first draft of it. The team's prompt (teamexperis_todo_list.png) pointed Bob at the already-drafted Problem Statement and asked it to break the project into an MVP task list "using the IBM Bob IDE," specifying a required numbering and priority format, which is the structure to-do.md still follows.

The Problem Statement itself went through a similar loop the other direction: the team wrote a first pass, then handed it to Bob along with the exact judging constraints (500 words, specific problem, target users, why it's creative) and asked it to tighten the draft against them (teamexperis_problem_statement_solution.png).

Infrastructure

The GitLab Docker stack was built and debugged in Bob, not just scaffolded. One session explicitly asked Bob to troubleshoot why ./manage.sh seed wasn't working against gitlab-local/docker-compose.yml (teamexperis_gitlab_container_debug.png). Another asked Bob to confirm, against to-do.md, whether Section 1 (Infrastructure) was actually complete before moving on (teamexperis_create_weatherapp_container.png) rather than assuming it from memory.

Skill authoring

The sdlc-harness skill scaffold (Task 17) started as its own Bob session: create a branch off dev, then plan the skill scaffold specifically (teamexperis_2b_task_17.png). SKILL.md was then built up incrementally across several follow-on sessions rather than in one shot, including a later refactor that folded a separate AGENT_ORCHESTRATION.md draft directly into SKILL.md once it became clear the two were describing the same thing from different angles (git log: ed21619 refactor: fold AGENT_ORCHESTRATION.md into SKILL.md).

MCP server and agent implementation

Sections 2A (the MCP server: GitLab client, issue/MR tools, work-item-format) and 2B (the five agents, review interface, telemetry) were built through structured, per-task Bob sessions rather than one continuous conversation. The Task 18/19 work in particular used an explicit plan file built around the subagent-driven-development convention: each dispatched task gets only its own step and the prior task's handoff summary, not the whole plan re-read every time, which keeps token cost from scaling linearly with plan length. One of these sessions (teamexperis_tasks2b18and19.png) shows a 91.5k/270k-token planning task for exactly this pair of tasks. A separate session (teamexperis_agent_skill_config.png) shows Section 3 (Tasks 27 through 31: Bob mode definition, model-usage rationale, MCP registry entry, agent orchestration design, skill unit tests) dispatched to Bob as one batch, at 1.2M tokens sent and an API cost of 2.41 for that session alone.

Tasks 20 through 26 — the five agents, the human review interface and the suggestion telemetry — were built in a single tracked session (teamexperis_tasks20-26_agents_build.png), 16 of 16 sub-tasks completed at a cost of 9.03 Bobcoins. The session summary maps each agent to its task number and source file, which is why the repo's module layout matches to-do.md one-for-one rather than approximately.

The agent design iterated rather than landing correctly on the first pass: a later commit (f0032a3 Tasks 20-21: agents produce a draft brief instead of templated prose) reworked the AC and Ambiguity agents specifically because their first version produced generic filler text ("the system responds correctly") instead of grounding output in the actual issue content, a change made after reviewing what the agents had actually produced.

That review round (teamexperis_tasks20-26_agent_fixes.png, 22.34 Bobcoins — the most expensive session in the project) was where Bob was used as a reviewer rather than a generator, and it found defects that the passing test suite did not. The most serious: applyFinding recorded a telemetry outcome of accepted for writes that never reached GitLab, so the acceptance-rate number the demo cites would have been computed from writes that never happened. Bob added a failed outcome excluded from both sides of the fraction. The same round fixed an acceptance-criteria detector that treated ordinary prose containing "given…when…then" as real criteria, and a verb-conjugation bug that rendered "When the user add dark mode toggle". Sixty of sixty tests passed both before and after, which is the point: the suite was checking that the plumbing ran, not that the output was correct.

The finished loop was then verified against a running GitLab instance rather than against mocks (teamexperis_live_gitlab_e2e.png, 12 of 12 at 6.42 Bobcoins). Bob drove the agents through the MCP tools only — no shell, no curl, no git — applied suggestions to real seeded issues, then re-read those issues back from GitLab to confirm the writes had actually landed. The same session reported what did not work alongside what did, including a port collision that stopped the demo site container from starting.

The weather app

The Weather Dashboard demo artifact (weather-app/) was built by a second team member in a separate Bob session, using Bob's own task/subtask tracking feature rather than a single freeform request: a six-item todo list (create index.html, styles.css, app.js, README.md, tests.md, then review and validate all files), tracked and checked off inside Bob's Tasks panel (Prasanna-weather-dashboard-session-summary.png).

Model usage

The skill asks Bob's built-in model to generate content at exactly two points: drafting Acceptance Criteria and rewriting Ambiguity findings, both grounded in issue text. Dependency, State-transition, and Coverage findings are deterministic TypeScript. The skill controls when generation is invoked, not which model Bob runs. The full-backlog Audit summary is the context-heavy step, while individual drafts are single-issue operations.
